# W-H 评估：DSH_HOME 是否迁往公共目录（Documents/dshdata）（2026-09-21）

> GOAL-ANDROID-GAP-2026-09-21 的 W-H 决策点交付物。
> 结论先行：**不迁**。判据、证据与「什么变化会推翻本结论」见下文。
> 用户数据的「不丢」由 W-B 备份/恢复（本 goal 已交付）+ 既有的「所有文件访问」
> 导出通道承担，而不是靠改变数据驻地。

## 背景

DSHA 把会话/设置/附件放在 `Documents/dshdata`（公开可见、卸载保留），
`DSH_HOME` 本体与凭据留私有目录。我方现状：全部数据在 `filesDir/.dsh`
（私有目录，卸载即丢——但运行时解压、会话、插件、设置全在一处）。

## 判据（评估前约定的决策规则）

| # | 判据 | 迁的收益是否覆盖代价 |
|---|---|---|
| J1 | **卸载不丢**是用户的真实高频痛点，还是备份能等效覆盖 | 备份（W-B）已提供「主动保全」；公共目录提供的是「忘备份时的兜底」 |
| J2 | 公共目录（FUSE/sdcardfs）能否承受我方 IO 形态 | 我方 IO = 2.4 万小文件（runtime 解压）+ 会话 jsonl 高频 append + 插件包读写 |
| J3 | scoped storage / 卓易通的行为风险是否可控 | 我方实测面含鸿蒙卓易通，其行为差异是已知未知数 |
| J4 | 迁移对既有机制的破坏面 | sentinel / 原子写 / link→rename / preflight / resilient-list 全部锚在私有目录语义上 |

## 逐项证据

**J1（痛点 vs 等效）**：W-B 已交付「导出 zip（凭据排除）+ 体检恢复」，且本 App 已有
`MANAGE_EXTERNAL_STORAGE` 通道（manifest + 首启引导）——用户要「文件管理器里可见的
副本」时，备份 zip 就是可见副本。「卸载不丢」的剩余价值 = 用户忘备份 + 卸载 的
**合取场景**——低频；而代价（J2/J4）是**常驻**的。收益/代价不成立。

**J2（IO 形态）**：公共目录在 Android 11+ 走 FUSE，每个文件操作多一次用户态往返。
我方最重的 IO 事件是首启解压 2.4 万小文件（私有目录下实测数分钟）——迁公共目录
会让这个本就敏感的路径**可预期地更慢**（FUSE 对小文件创建的开销是数倍于 ext4
私有目录；这是 Android 公开结论，非推测）。会话 jsonl 的 append 频率（每条消息
若干次写 + fsync 语义）在 FUSE 上同样有已知劣化。runtime 本体**绝对不能迁**
（dlopen/exec 语义在公共目录不成立），则「迁」实际 = 只迁 `.dsh`——但 `.dsh`
里的 profiles/node_modules（插件包，数千小文件）同样受 FUSE 惩罚。

**J3（卓易通）**：卓易通对「所有文件访问」与公共目录的行为**没有实测数据**
（B-DEVICE 清单开放项）。在私有目录语义已被实证（鸿蒙 6 全链路跑通）的情况下，
迁公共目录是把一个已实证的确定性换成未实证的未知数——对本项目「鸿蒙是独占
生态位」的战略是直接负资产。

**J4（机制破坏面）**：sentinel 重解压、原子写发布（temp+rename）、link→rename
补丁、preflight 会话完整性、resilient-list 隔离——全部假设「目录语义 = 标准
Linux 文件系统」。FUSE 上的 rename/fsync/权限位语义有已知边角（权限位丢失、
rename 跨目录语义弱化）。每一项都是重新踩坑面，且踩坑形态是**数据安全**——
恰好是迁移想保护的东西。

**附带风险（DSHA 也承认的形态）**：公共目录 = 用户/三方 App 可读写。会话 jsonl
被文本编辑器「看一眼存一下」就可能触发 preflight 的 corrupt 判定；网盘自动同步
目录（用户常把 Documents 纳入同步）会造成并发写与隐私外泄面。

## 决策

**不迁。**「不丢数据」的完整方案 = 已交付的三层：

1. **W-B 备份/恢复**（本 goal）：主动保全 + 体检恢复；
2. **「所有文件访问」通道**（既有）：文件管理器级直读直写，高级用户自取；
3. **卸载前的系统级提示**：Android 本身在卸载页不提示数据——可在未来版本
   考虑「定期自动备份到公共目录」增强（把「忘备份」的合取场景再削一层），
   那是 W-B 的增量，不是数据驻地变更。

**推翻本结论的条件**（任一成立则重开评估）：
- 社区反馈显示「忘备份 + 卸载」造成真实数据丢失的**高频**案例；
- Android 后续版本改变公共目录 IO 语义（FUSE 开销显著下降）；
- 卓易通实测证实公共目录行为与原生一致且性能可接受（B-DEVICE 回填）。

## 与 DSHA 的形态差异说明（写进对外口径用）

DSHA 的公共目录方案适合它：它的数据 = Ubuntu rootfs 里的用户文件（本就慢路径），
且它没有 sentinel/原子写这类锚在私有目录语义的机制群。两家的「不丢」哲学不同：
**DSHA 是「数据放在丢不了的地方」，我们是「给你一条可靠、可体检、凭据分离的
备份通道」**——前者赢在兜底，后者赢在 IO 性能与机制简单，且我们的备份是
跨设备可移植的（公共目录方案换机依然要手动拷）。
