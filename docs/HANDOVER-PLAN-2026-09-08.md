## 二、主史挖出的、改变结论的关键事实

### 事实 A：头号真凶是构建/部署断链，不是代码质量

主史 seg14 有明确结论——**"越修越多"的真凶是构建/部署断链**。六种形态反复出现：

| 形态 | 后果 | 证据 |
|---|---|---|
| build 脚本 UTF-8 BOM 丢失 | APK 静默失败 | L26567、R35 |
| WebView 磁盘缓存跨重启存活 | 热推后跑旧前端 | L26842（坑 #15） |
| 热推 staging 旧包 | 推了等于没推 | L27474 |
| MainActivity 改动未提交 | APK 无文件选择桥 | L27800 |
| 哨兵只增不删 | build-info 恒报最旧 | BUG-009 |
| 源码改于构建之后 | 修复根本没进包 | L27918 |

**这直接解释了你那句"我装的是最新包啊"（L27322、28012）。**
含义是：你当前的 bug 池里混着一批**"已修但未生效"**的条目。不先把这一族分离出去，
后面修任何东西都可能白修，而你会继续觉得"修了又冒"。

### 事实 B：同文件并行编辑，踩了 8 次以上

L21539、22020-22022、22126、22475、20068、20242、18166、18194，外加 R6、R35。
后果不是"偶尔出错"，是**救命的修改被静默吃掉**（`mode: ptc` 那次差点让会话恢复全线失败）。

### 事实 C：静默失败是主力，而单测结构上测不出来

第 3 轮 34 个 bug 里，"静默"是高频词：多 JSONPatch 只解析第一个、未知 op 落兜底赋值、
`setChatMessages` 丢 `is_hidden`、`getChatMessages` 整个丢弃第二参数、变体缓存永久 `[]`。
670 个单测断言的是"不抛错 + 200"，而静默失败恰好满足这个断言。

## 三、新方案：四层，按"先止血、再对齐、后精确"排序

### 第 1 层｜构建-部署可验证链（最高优先，先做）

**目的**：把"已修但未生效"从 bug 池里清出去。这一层不做，后面所有修复的有效性都无法确认。

- APK 内嵌构建指纹：`sentinel + 每份 bundle 的 md5 + 源码 git commit hash`，诊断面板一眼可核对
- 哨兵唯一化（发布新即清旧），根治 build-info 恒报最旧
- 热推脚本：推前记录字节数、推后校验必须变化，不变即报错（不要"报成功但产物旧"）
- WebView 缓存对策：热推后强制 bypass（版本号进 URL 或 no-store）
- 构建脚本 BOM 断言：无 BOM 直接 fail，不允许静默
- **一条命令出"当前设备跑的是哪份代码"的真相报告**

### 第 2 层｜Golden Master：把你的验收标准机器化

你的标准一直是"和 ST 看上去一致"。这一层不是新发明，是**把它变成可判定**。

- ST 侧（Luker 2.2.2，node_modules 349MB 齐全，可跑）：跑 pilot card，录基准
- 采集五项：最终 prompt 全文 / 渲染后 HTML / 变量树快照 / 激活 WI 条目 / 状态栏输出
- DSHT 同卡同输入回放 → 逐项 diff
- 渐进：先只 diff「第 1 轮 prompt 全文」（零 LLM 依赖，含预设排序/正则/WI/宏/depth 全部结果）

### 第 3 层｜21 份 `@types` 契约对质

字段形状静默偏差被复盘文档判为**最危险**一类。方法已在正则模块验证可行：
11 个业务字段 9 个偏差，且抓出 5 条既有审计未覆盖的高危（含 `enabled`/`disabled` 极性反转）。

- 剩余 21 份：`chat_message` / `lorebook_entry` / `variables` / `worldbook` / `preset` / `character` / `generate` / `inject` …
- 每份产出对照表 + 契约断言测试（断言值取自 `.d.ts`，注释标 ST 行号）
- 把 52.8% / 31.7% / 41.7% 换成**未加权的精确数字**

### 第 4 层｜纪律固化

- 同文件严格串行编辑（8 次教训）
- 每 Tier 1 修复落回归（测试 / 模拟器探针 / 真机清单三选一），否则不算完成
- 改动做进通用 RP 插件，禁止单卡特配
